Part 1 · Flows

What the person does, what the cloud does

Ten flows cover the product; the composer gets its own section after them. Each flow names the agents and the model tier that runs them.

what the person sees system step model call, tier named decision event from the run

F1 · Boot and first run

Preloader → run view. On a fresh install the first goal typed into the composer becomes the first workstream.

F2 · Start a run

Ultra plans once and the plan card shows before anything else spends. Super and Nano do the work concurrently.

F3 · Approval gate

The only time the cloud turns orange on purpose. Nothing is sent, written or run outside the sandbox until a decision.

F4 · Artifact versions

Writer output lands in the Inspector's Artifact tab; a change request in the composer bumps the version.

F5 · Learning loop

Run two knows what run one learned. Nano does all of it after run.end.

F6 · Inside chat apps via OpenClaw

Nimbus is the model; OpenClaw is the messenger. Approvals never happen in chat, only a link to the web composer.

F7 · Always on

Two schedulers, one run table. Headless runs auto-approve only low-risk actions.

F8 · Router and fallback

Per hop. The role tier is a ceiling; the router never falls up.

F9 · Eval gate

Grades every hop, not just the final answer. A red check blocks the PR.

F10 · Run status

What the header pill, the cloud and the rail show at each run state.
Part 1b · Composer states, in full

One box, six states, fourteen transitions

The composer never changes shape. Only the placeholder, the primary button, the secondary button and what Enter does change with state, so the person can always predict what pressing Enter will do. The diagram shows the states; the two tables under it are the contract the build follows.

How each surface is built
